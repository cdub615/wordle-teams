### Maintenance mode

**Walked 2026-09-04 against `beta.wordleteams.com`, from the ATL edge.** The
owner flipped the var in the dashboard both ways; every observation below is a
measured response, not an inspection of the code that produces it.

- [x] Flip `MAINTENANCE` to `true` in the Cloudflare dashboard.

      **It is a Deploy, not a Save, and that is worth knowing before an
      outage.** A Worker var is part of a VERSION, so the dashboard mints and
      rolls out a new version rather than editing a value in place. Recorded in
      `v2/src/lib/maintenance.ts`, whose header had claimed the flag "takes
      effect WITHOUT A CODE DEPLOY" — true of code, misleading about the
      button.
- [x] `/app`, `/me`, `/complete-profile`, `/login` and `/` all 307 to
      `/maintenance` — **all five**.
- [x] `/home`, `/about`, `/privacy`, `/terms` **stay up** — deliberate. All four
      answered 200 throughout.
- [x] **`/` DOES NOT NEED A CACHE PURGE. THE ROW ABOVE THIS ONE USED TO SAY IT
      DID, AND THE PREMISE WAS FALSE** (`wt-ksh.8.52`, closed by this walk).

      It read: "`/` is genuinely cached at the edge — a cached 200 outlives the
      flag and the Worker never sees those requests. Purge the apex, or
      redeploy." That describes a CDN edge cache sitting in FRONT of the Worker.
      This is not one. `wt-ksh.8.45` measured that `s-maxage` on a Worker
      response reaches no Cloudflare edge cache at all; `wordle-teams-fqeq` then
      bought the caching back through the **Cache API, inside the fetch
      handler**. That is a store the Worker consults, not a layer that can
      answer ahead of it — and `src/server.ts` consults it strictly downstream
      of the gate (`withMaintenanceGate` delegates to
      `withCachePolicyOnDocuments` only when the request is NOT gated, so
      `cache.match` is never called for a gated path). The Worker runs on every
      request to the custom domain, so a stored `/` cannot outlive the flag.

      **Measured, not just read:** `/` was warm at the ATL edge
      (`x-doc-cache: HIT`, `age: 12`, three consecutive requests) immediately
      before the flip, and answered 307 on every request while maintenance was
      on.

      **What remains is client-side and no purge reaches it.** `/` ships
      `stale-while-revalidate=604800`, so an individual visitor's own browser
      may serve them the pre-outage landing page while it revalidates. One
      visitor rather than everyone, self-correcting on the next navigation, and
      outside the reach of any zone purge — a property to know, not a step to
      run.

      Also confirmed while the flag was on, since it is the direction
      `src/server.ts` argues about: every 307 carried `private, no-store` with
      **no `s-maxage`**, so a maintenance response is never published with
      shared freshness.
- [x] Flip it back to `false` and confirm the site returns — all nine paths
      back to their baseline behaviour (`/` 200, `/app` 307 to `/login`, `/me`
      307 to `/app`, `/complete-profile` 307 to `/login`, `/login` 200, the four
      static pages 200).

      **A repo deploy also flips it back.** `wrangler.jsonc` carries
      `"MAINTENANCE": "false"`, so the next `wrangler deploy` overwrites the
      dashboard. A safety net against leaving the site dark, and equally a way
      for a routine deploy to end an outage banner without anyone deciding to.

- [x] Icons and name correct — confirmed 2026-09-04, on the launcher and in the

- [x] **THE PRODUCTION INSTALL REQUIRED BY THE start_url ROW BELOW EXISTS**, and
      has for some time. That is the stronger form of the artifact that row asks
      for: it was made against production's `start_url: "/me"` well before
      cutover, so it is an aged install carrying the old entry point rather than
      one manufactured to order. Both v1 and v2 are installed side by side.

      This is the one item in this document that **cannot be recovered if it is
      lost**. After the DNS flip, production's manifest is v2's and says
      `/app`, so no new install can ever carry `/me` again. Do not remove or
      reinstall the v1 install before cutover.
- [x] **An install carrying the OLD `/me` start_url still lands correctly** —
      resolved 2026-09-03, and the risk turned out to be structurally covered.

      **The manifests, measured:** production ships `start_url: "/me"`, beta
      ships `start_url: "/app"`, and **neither declares `scope`**. With no
      `scope`, the default is the `start_url` with its last segment removed —
      `/` in both cases. So `/me` and `/app` are both in scope, and the redirect
      **cannot** kick a standalone window out to the browser, which was the
      actual failure mode worth worrying about. `/me` answers `307 -> /app` on
      beta, confirmed by request.

      **WHAT STILL CANNOT BE TESTED BEFORE CUTOVER, and the preparation that
      makes it testable ON the day:** no beta install can carry `/me`, because
      beta's manifest says `/app`. The only artifact that reproduces this is an
      install made from **production** — so **install the PWA from
      wordleteams.com now and keep it**. On cutover day, launching that install
      IS the case, with nothing to simulate.

      **`/me` MUST NEVER BE REMOVED.** Every pre-cutover install depends on it
      permanently, and the route is the only thing standing between those users
      and a dead app icon. See `wordle-teams-cog5`: the route file calls the
      redirect "PERMANENT" while the wire says 307. **307 is the safer of the
      two here** — nothing is cached, so a browser re-asks on every launch,
      where a 301 would be cached by exactly this population and is irreversible
      in every browser that has seen it. The wording is what should change, not
      the status.
